# 企业 Agent 与知识库：工作原理设计

> 状态：草案 v2（2026-09）。本文回答三个问题：**① 知识库怎么导入、数据存哪；② 对话时 AI 怎么查到知识库、
> 提示词长什么样；③ agent 完整工作流程**。架构决策记录与退役清单在附录，不阻塞阅读。
> 交付形态：**B 私有化交付**（每套部署 = 一家企业）+ **兼容演进到 C 多租户 SaaS**（存储自第一天按租户布局，
> 见 §1.3/§1.4）。

## 一、加知识库后怎么工作：数据怎么导入、存到哪里

### 1.1 用户看到的操作

```
库管理页（前门）
  ├─ 新建库：填名称「研发规范」→ 选择类型（人写 / 文件导入）
  ├─ 导入内容：拖入文件或选目录 —— 规范.pdf、评审规范.docx、docs/ 目录、粘贴网页 URL
  ├─ 看库状态：文档数、索引状态（构建中/已就绪）、最近同步时间
  └─ 对话时勾选：新对话的输入框旁「＋知识库」选择挂哪几个库
```

### 1.2 数据流（每一步落在哪）

```
拖入 规范.pdf
   │
   ▼ POST /api/knowledge/kbs                      创建库
   ▼ POST /api/knowledge/kbs/<id>/import          上传/登记文件
   │
   ├─① 解析（导入时一次性完成，之后不再解析）
   │     .md / .txt        → 原样保留
   │     .pdf / .docx      → 提取正文转 Markdown（纯 JS：unpdf / mammoth）
   │     目录               → 递归处理
   │     每篇生成的 Markdown 头部补 frontmatter：来源文件名、导入时间、原格式
   │
   ├─② 落盘（原文永远在磁盘 —— 这是 agent 能直接 read/grep 的前提）
   │
   │   ~/.pi/knowledge/kb-yanfa-guifan/            ← 库的根目录（每库一个目录）
   │     ├── kb.yaml                               ← 库元数据：名称、类型、信任级、
   │     │                                             embedding 签名、创建者、共享范围
   │     ├── files/
   │     │     ├── 发布流程规范.md                    ← 解析后的正文
   │     │     ├── 代码评审规范.md
   │     │     └── attachments/                     ← 文档里的图片等附件
   │     └──
   │
   └─③ 建索引（异步后台任务；索引是缓存，删了可随时重建）
       │
       │   ~/.pi/cache/knowledge/kb-yanfa-guifan.idx
       │     每篇文档一条记录：
       │     { path, title, mtime,
       │       terms: {...},          ← BM25 词频（关键词检索用）
       │       vector: [0.02, ...] }  ← 384 维语义向量（e5-small 本地模型算出）
       │
       └─ 增量规则：再次导入时按 mtime 对比，只处理新/改过的文件
```

**三条铁律：**
1. **原文落盘优先**——库坏了、索引删了，文件还在，重新索引即恢复；
2. **索引是缓存不是数据库**——检索快靠它，但系统不依赖它存活；
3. **同步库只读**——将来接 wiki/飞书同步的库，agent 不能改；能写的只有 learnings 库（见三.4）。

### 1.3 库存在哪、谁能看到

- 所有库在**部署级**目录 `~/.pi/knowledge/<tenant>/kb-<slug>/`（跟 pi 数据主目录走，可环境变量重定位）——
  不属于任何工作区。**`<tenant>` 是租户层**：当前部署只有一个默认租户，成本为零；将来 B→C 演进
  （一套部署多家公司）或多部门隔离时，直接加租户目录，**库不用搬家**；
- **可见性 = 绑定**：谁挂了「研发规范」库，谁的对话才能搜到它。没绑定的对话，这个库对 AI 完全不存在；
- 每个工作区自动带一个**私有 learnings 库**（agent 沉淀经验用，别的部门看不到）。

### 1.4 规模上限与升级路径（能不能百万级文档）

关键事实：**检索永远只扫「绑定的库」，不是全系统总量**。100 家公司 × 1 万篇 = 总量 100 万，
单次查询仍只扫当前对话绑定的一两个库（万级），暴力点积 1ms。**暴力扫的敌人是单库规模，不是总量。**

| 规模 | 检索方式 | 存储格式 | 结论 |
|---|---|---|---|
| 总量百万、单库万~十万 | 现方案：分库 + 每库暴力点积 | 每库一个索引 JSON | **现设计直接覆盖** |
| 单库 30 万+ / 扫描 >50ms | 换 ANN 索引（hnswlib-wasm，纯 WASM 无原生编译） | 二进制文件 | `VectorStore` 接口后**一处替换**，接口不变 |
| 单库千万级 | 独立向量服务 | 向量数据库 | 预留缝，不预建 |

工程姿势：P2 实现时把向量存取藏在 `VectorStore` 接口后（暴力 JSON 为第一实现），ANN 升级触发条件
（单库 ≥30 万条或扫描 >50ms）写死在文档——**不为没到来的规模预先建库，但留好替换缝**。

## 二、对话时 AI 怎么查到知识库：提示词全景

### 2.1 从你按下发送，到模型看到什么

```
你：新建对话，勾选 [研发规范] [产品X] 两个库
你：「发布流程里测试不通过能上线吗？」
        │
        ▼ POST /api/agent/new { message, knowledgeBindings: ["kb-yanfa-guifan", "kb-chanpin-x"] }
        │
        ▼ daemon 创建会话时装配三样东西给模型：
```

**模型每轮看到的上下文（知识问答会话形态）：**

```markdown
┌─────────────────────────── system prompt ───────────────────────────┐
│ (pi 基础提示词)                                                       │
│                                                                      │
│ 你绑定了以下知识库，回答事实性问题必须先检索、引用来源：              │
│  - 研发规范（人写规范，24 篇，高信任）                               │
│  - 产品X（wiki 同步，156 篇，中信任）                                │
│ (此段由绑定动态生成 —— 绑什么库写什么，不绑则整段不出现)             │
│                                                                      │
│ (AGENTS.md 环境契约，逐字注入，<2KB：协作规则/git 规范，无知识内容)  │
└──────────────────────────────────────────────────────────────────────┘
┌─────────────────────────── 工具表 ──────────────────────────────────┐
│ kb_search —— 跨绑定库混合检索                                         │
│   参数: { query: string, limit?: number,                             │
│           filters?: { kb?: string, tags?: string[] } }               │
└──────────────────────────────────────────────────────────────────────┘

┌── user ──┐  发布流程里测试不通过能上线吗？
└──────────┘
```

**关键点：AI 知道「有哪些库」靠两处确定性机制**——动态生成的提示词段落 + `kb_search` 工具描述。
**不靠** AGENTS.md 里的引用（那是旧方案，模型跟不跟随全凭心情，已废弃）。

### 2.2 一轮对话逐帧回放

```
① 模型读到问题 → 判断需要事实依据 → 发起工具调用:
     kb_search({ query: "发布流程 测试 上线" })

② 工具执行（对 AI 是黑盒，~50ms）:
     BM25 关键词路: "发布流程" 命中《发布流程规范.md》
     向量语义路:   "测试不通过能上线" ≈ 文中"测试未通过禁止合入 release 分支"
     两路融合排序 → MMR 去重 → 取 top 5

③ 模型收到 toolResult:
     { results: [
        { kb: "研发规范", path: "files/发布流程规范.md",
          title: "发布流程规范", score: 0.83,
          snippet: "3.2 发布门禁：自动化测试全部通过后方可合入 release 分支……" },
        { kb: "产品X", path: "wiki/回归策略.md", score: 0.41, ... } ] }

④ 模型生成回答（引用来自检索结果的 path，UI 渲染成可点击来源）:
     "不能。按《发布流程规范》3.2 节：自动化测试全部通过后才能合入 release
      分支。[来源: 研训规范/发布流程规范.md]"
     └─ UI 上 [来源] 点击 → 直接打开该文档（文件就在磁盘上，秒开）
```

### 2.3 检索不到时（诚实退化）

- 两路分数都低于门限 → 返回空 + 提示「知识库中未找到」，**模型不编造**；
- 没配 embedding 模型 → 自动退化为纯 BM25（关键词还能搜，语义搜不了，系统照常工作）；
- 你问的其实是代码/文件 → agent 形态下模型直接 `read`/`grep`，不走知识库。

## 三、Agent 完整工作流程

### 3.1 会话生命周期（两种形态，同一底座）

```
发起对话
   │
   ├─ 形态A：知识问答会话（新用户的前门）
   │    无文件工具，只有 kb_search；检索结果直接进回答；每答必带来源
   │
   └─ 形态B：agent 会话（干活的，现 pi-web 会话的超集）
        全套工具（read/write/bash/派 subagent/工作项/loops…）+ kb_search
        知识不是回答素材，是「干活时查的规范」
```

### 3.2 agent 会话的一个完整回合（知识在其中的位置）

```
你：「按公司规范给这个模块加上错误处理」
   │
   ▼ ① 模型先看环境：读 AGENTS.md（常驻），ls 代码目录，read 相关源文件
   ▼ ② 模型需要"公司规范"→ kb_search({query: "错误处理 规范"})
   │      命中《代码评审规范.md》第 4 节: "所有 IO 调用必须捕获并分类错误…"
   ▼ ③ 按规范写代码（edit 工具，改动出现在文件面板/改动列表）
   ▼ ④ 跑测试（bash 工具）验证
   ▼ ⑤ 汇报: "已按《代码评审规范》4.2 节为 3 处 IO 调用添加错误分类处理，
   │         测试通过 [来源: 研发规范/代码评审规范.md]"
   ▼
   整个回合模型自主决定何时查知识库 —— 工具描述里写明"本会话可检索XX库"，
   模型在需要时自己调，不需要人提醒
```

### 3.3 从发送到回复的完整链路（系统视角）

```
浏览器 ──POST /api/agent/[id]──▶ web server（纯代理）
                                    │
                                    ▼ pi-daemon（会话的唯一持有者）
                              AgentSession（装配：system prompt + 工具表 + kb_search 绑定）
                                    │
                                    ▼ 模型 API（按你的模型配置调用）
                              ◀── 工具调用请求(kb_search/edit/bash…)
                              工具执行 → 结果回填 → 模型继续 → …循环直到完成
                                    │
浏览器 ◀──────SSE 流式推送（每个字、每次工具调用实时可见）──────┘
```

### 3.4 知识的回流（learnings，为什么库有「类型」字段）

```
agent 会话/loop 轮跑完
   ▼ learner 角色做「泛化测试」：这条教训删掉细节还是通用规则吗？
   ├─ 是（如"改依赖必须跑全量测试"）→ 提议晋升 → 人审核 → 进企业级库（全员可搜）
   └─ 否（如"本项目 A/B 模块循环依赖"）→ 留在本工作区私有 learnings 库
   （cxin 已有的机制，原样平移，只是存储位置从工作区仓库变为部署级库）
```

## 附录 C：落地切片（每片独立可验证）

- **P1 导入建库**：库存储+API+文件解析+BM25 索引+管理 UI。验证：上传真实文档→建库→会话内 kb_search 搜到。
- **P2 知识对话**：会话绑定+向量层+融合/MMR/门控+引用 UI+首页前门。验证：「申请服务器权限」命中《资源申请流程》；回答带可点击来源。
- **P3 agent 绑库**：workspace 默认绑定、learnings 自动库、旧 knowledge 子系统退役。验证：loop 轮写 learnings 到新位置；晋升手动走通。
- **P4 连接器+治理**：DaemonJob 同步框架+首个外部源+晋升审核 UI。验证：外部增量同步→检索面自动更新。
