# 第一阶段：六层架构收敛与工作项管理

日期：2026-10-23

状态：用户已批准（2026-10-23）；未实施。实施计划见 `../plans/2026-10-23-m1-single-process-host.md` 与 `../plans/2026-10-23-m2-work-items-management.md`。

## 1. 意图与已确认决定

用户希望 Pi Web 从“导入需求、启动一次 loop”的辅助工具，逐步发展为可以管理需求交付的产品。
当前首先交付架构收敛和可用于日常工作的工作项管理，后续再加入设计、开发、验证、发布准备角色的自主领取与自动执行。

审阅摘要：工作项有完整中央页和聊天快捷查看；先保留旧项与旧 loop，标准流程由人显式启用；标准流程通过人工确认和证据记录推进。
没有发布依据的旧“完成”不会变成“已发布”，已发布记录也不会因修改需求而被重新解释；新增需求使用关联后续项。

本设计直接沿用聊天中已确认的决定：

1. 六层为：pi-web 前端、Next.js 应用接口、pi-extension、原样 pi SDK、文件与状态、部署基建。
2. 去掉独立 daemon，改为 Next.js 常驻 Node.js 单实例宿主。关闭浏览器不停止后台执行；服务重启中断执行，依文件记录接续。
3. pi SDK 源码、依赖版本和原有通用职责保持不变。业务角色、工作项规则和 loop 属于扩展层，不进入 SDK。
4. 当前阶段包含工作项管理，角色自主领取与执行放后续阶段。
5. 外部同步脚本将需求导入 Pi Web 后，以 Pi Web 为业务权威，不做禅道双向状态同步。
6. 工作项采用方案 A：中央独立管理页为主，右侧面板作为聊天时的快捷查看入口。

这是一个涉及会话宿主迁移与管理面的项目，按两个可独立验收的里程碑推进：先保持现有功能并收回宿主，再交付工作项管理。
本文规定最终行为与边界；具体实现任务、测试次序和执行方式由后续实施计划给出。

## 2. 目标、范围与明确排除

第一阶段完成：

- 会话创建、消息、状态、SSE、停止、子 agent、既有 kit loop 在一个 Next.js Node.js 宿主内运行。
- 取消 daemon 的网络服务、客户端代理、sidecar 拉起、健康探测和独立运行命令。
- 工作项拥有独立中央页、列表/看板、详情、创建编辑、附件、来源、优先级与筛选、流程动作、关联会话和审计历史。
- 程序化导入去重与本地权威保护；已有工作项、来源和会话文件可读、可恢复。
- 明确的人工交付流程与检查记录，为后续 agent 调用同一套扩展服务准备边界。

第一阶段不包含：新建四类自动 worker、TaskPool/ClaimService 的领取执行协议、自动调度模型、自动生产部署、
子任务 DAG、多人账号/组织/权限体系、迭代/工时/甘特图、新来源连接器、通用拖拽工作流编辑器、远程或多副本会话宿主。
既有 loop 可以继续按原合同工作；这不等于新增多角色自动交付已经完成。

反目标：不能只删 daemon 入口却留下代理依赖；不能在 Extension 名下复制模型循环；不能把旧 done 当作已发布；
不能让中央页和右侧面板各自拥有一份业务状态；不能把扩展服务调用转换成一次不必要的 LLM 调用。

## 3. 方案选择

### 3.1 会话与业务架构

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| Next.js 单实例宿主 + 业务扩展 + 原样 SDK | 移除跨进程代理和 sidecar；服务重启需恢复执行 | 用户选择 |
| 保留当前统一 session daemon | Web 重启时会话可以继续，但需要独立进程、代理和跨进程状态管理 | 不采用 |
| 普通会话在 Next.js、后台执行独立 worker | 分离两种生命周期，但仍要维护两种会话所有权与控制通路 | 当前不采用 |

### 3.2 工作项管理主界面

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| A：中央独立管理页 + 右侧快捷查看 | 足够空间管理多条需求、详情与产物，同时保留聊天联动 | 用户选择 |
| B：只增强右侧窄面板 | 导航改动较少，但复杂需求与跨阶段管理受宽度限制 | 不采用 |

### 3.3 数据权威

用户选择“脚本导入后 Pi Web 为准”。同步脚本作为输入适配器，阶段、优先级、需求修订、确认和交付记录均由本地管理。
来源编号、链接和初始导入内容用于溯源，不形成另一套实时业务权威。

## 4. 六层与模块边界

![六层目标架构](assets/work-item-delivery-single-process.png)

架构图中的角色唤醒、任务领取和四类角色表示后续能力的归属，不全部属于第一阶段实现范围。

| 层 | 第一阶段职责 |
| --- | --- |
| ① 用户交互 | 现有会话界面、中央工作项页、聊天侧栏、人工决策与配置 |
| ② Next.js 接口 | 认证、输入解析、错误映射、事件流、调用扩展服务或 SDK 宿主入口 |
| ③ pi-extension | 工作项业务/流程/存储适配/工具、kit loop 宿主逻辑、subagent、知识检索等扩展 |
| ④ pi SDK | 原有 AgentSession、模型/工具循环、资源与扩展机制、SessionManager、基础工具 |
| ⑤ 文件与状态 | 工作项 YAML/正文/事件/附件/产物、工作区配置、会话 JSONL、临时运行记录 |
| ⑥ 部署基建 | 一个常驻 Next.js Node.js 宿主、本地文件、Git/worktree、命令进程与退出处理 |

“扩展层”表示代码职责，不要求每个业务函数都注册成 LLM 工具，也不要求为了目录命名而大规模搬迁无关文件。
现有 `lib/work-items/` 可作为工作项扩展模块，导出供 HTTP 使用的确定性服务，并注册供会话使用的工具；两种入口共用业务实现。

通用宿主胶水负责 SDK 会话注册、资源装配、SSE 连接和启停，不知道需求有哪些阶段。
工作项流程只在扩展内部；loop 的定时/合同逻辑只在 loop 扩展内部。Next.js 启动时调用扩展后台入口，不依赖碰巧打开一个会话。
不能把 SDK 的 session_start/session_shutdown 钩子误当作已经存在的进程级后台任务生命周期接口。

## 5. 单实例宿主与 daemon 移除

### 5.1 进程内会话入口

将当前 `lib/daemon/rpc-manager.ts` 的本仓 wrapper、注册表和 SDK 装配迁到中性的会话宿主模块。
这是移动和适配本仓代码，不是修改 `@earendil-works/pi-*` 依赖。
API 使用类型化宿主门面直接创建、命令控制、查询、停止和订阅会话；普通会话、子 agent 和 loop 轮共享同一注册表。

注册表、启动中的会话 Promise、后台入口注册与退出状态通过单例宿主持有。路由冷加载、模块重复装载、开发热重载不得创建第二个 owner 或第二套心跳。
会话资源装配继续尊重项目可信设置、工作区 capabilities/skills、Agents 配置和现有工具过滤行为。

现有 `/api/agent/new`、`/api/agent/[id]`、会话/运行集合 SSE 与 `/api/subagents/[id]` 保持浏览器协议。
不能在宿主已经接受 prompt 后，把缓存更新或响应发送失败误报为 accepted=false；现有拒绝/传输不确定语义继续保留。

### 5.2 事件与文件生命周期

SSE 直接订阅本进程会话与运行集合，保留 connected 帧、心跳、销毁通知、积压上限和慢客户端断开策略。
断开一个 SSE 连接只取消该订阅，不销毁正在执行的会话；重新连接可以取得当前状态。

SSR 初始会话数据、会话列表 live 合并、locate、detail、state、自动命名、归档/删除、信任变更和配置 reload 全部切换到本地门面。
新会话及子会话的 sessionId→sessionFile 缓存、空而有效的详情占位和会话自链接行为继续保留。
归档、删除与资源重载先处理活跃 wrapper，再移动文件；读取历史详情不新建另一个相同文件的写会话。

### 5.3 既有 loop 与子 agent

loop 的声明、cron、暂停、轮锁、到期补跑、开场合同、STATE、手动运行/停止和关联工作项逻辑保持现有协议。
loop 扩展从宿主取得创建/停止/查询会话接口，在 Next.js 服务启动时注册一次心跳，在退出时停止新轮并终止当前轮。
高频 tick 不创建重复定时器，手动轮与定时轮继续使用同一份锁/合同实现。

子 agent 扩展保留角色解析、工具/技能/扩展过滤、独立上下文、队列、worktree 与持久化元数据。
普通交互、子 agent 和 loop 继续通过现有会话 UI 可定位与控制。不得因为搬迁恢复已移除的社区包或增加第二套执行引擎。

### 5.4 退出、重启与一次性部署迁移

宿主退出先停止新消息和新后台轮，再中止活跃模型调用与受管理命令，写入可恢复的中断信息，关闭 SSE 并释放持有者自己的运行占用。
执行命令需要能定位本执行所属的进程组；不能使用“杀整个工作区 cwd 下所有进程”的方式处理共享 Next.js 宿主，以免误杀其他会话或开发服务。
无法证明旧命令已停止时，记录需人工处理的中断，不自动把同一项重新执行。

重启恢复读取会话与工作项文件，不续接丢失的网络请求，也不默认重新发送最后一条用户消息。
普通会话由人继续；既有 loop 按原补跑协议决定下一轮，并遵守未确认中断的阻塞规则。

未确认中断保存为工作区 `.pi/runtime/executions/<runId>.json`，至少记录 loop/session/item 关联、主机与命令进程身份、目录、停止结果和需处理原因。
loop 中断只阻塞该 loop 的新轮；交互会话中断只阻塞对应执行的自动接手，不暂停整个工作区。
Loops 面板显示“执行中断，待恢复”并提供“重新检查并恢复”动作；关联工作项可跳转到这一记录。恢复 API 重查旧会话和已知命令进程。
已证明停止则解除；已证明仍活动则拒绝；历史身份缺失而无法自动证明时，允许用户先在本机处理，再显式登记已停止，记录该人工声明和诊断结果。
人工声明不能覆盖服务实际探测到的旧进程仍活动，也不能被定时器自动生成。SDK 无需为这些扩展恢复记录增加机制。

首次部署必须安排旧 Web/daemon 的停机切换，确保旧 owner 与其活动命令结束，再启动单实例宿主。
新版不自动按端口杀未知进程；发现旧配置指向仍活动的 daemon 时给出明确迁移错误，不能悄悄同时成为会话写者。
原有文件布局继续可读，不在此迁移中移动用户会话或工作区目录。部署交接步骤由实施计划列出。

移除 `bin/pi-daemon.js`、独立 daemon HTTP 服务、daemon client、agent-proxy、sidecar 拉起及相关运行命令与失效配置。
先迁出仍需的 wrapper、SSE writer、进程管理与测试，再删除空壳；保留 `packages/pi-loop/` 的独立 CLI/纯协议能力。

## 6. 工作项管理体验：方案 A

### 6.1 入口与作用域

新增工作区作用域的中央 `WorkItemsPage`。工作区总览的工作项入口及右侧“打开完整管理”都进入该页。
现有右侧 rail 的工作项图标保留快捷面板，面板顶部提供完整管理入口；不把同一图标的单击同时解释成两个动作。
新建工作项从总览/完整页进入中央页表单；聊天侧栏可提供快捷创建，成功后共享数据更新。

中央页明确绑定 workspaceId。不能使用当前聊天 tab 的 activeWorkspace 代替页面身份，避免打开另一个工作区的管理页时误写项目。
工作区切换使用页头选择器，切换前处理未保存草稿。没有 work-items capability 时显示未启用，不隐式修改 capabilities。

复用现有 CenterPage 承载中央页，不把需求伪装成聊天 tab。会话 tab 的身份与持久化模型保持原语义。
中央页隐藏配置页式的聊天顶部 chrome，并收起右侧 dock，为列表/详情提供管理空间；返回聊天恢复对应会话的 dock 状态。
点“查看/开始会话”关闭中央页并打开对应工作区的会话，右侧定位该工作项，允许从侧栏回到原详情。

工作项深链使用 `?workspace=<id>&page=work-items&item=<key>`，不与现有 view=chat/overview 语法混用。
解析入口先识别工作项页面，再走现有 tab URL 投影；刷新、前进后退和无效 ID 都有确定行为，不因聊天 tab 的 URL effect 覆盖管理页深链。
URL 与路由具体 helper 名称由实施者决定，但必须复用一个解析/生成协议并测试往返。

### 6.2 列表、看板与详情

默认列表，支持切换阶段看板；偏好按工作区保存。列表/看板共享同一筛选：搜索、类型、阶段、优先级、来源、阻塞/待确认、活动/归档。
按 P0→P3、更新时间、key 稳定排序；不新增账号、指派人或工时模型。
列表显示 KEY、标题、类型、阶段、优先级、阻塞/待确认标记、来源与更新时间。
看板仅展示阶段投影；首版不通过自由拖动跳过确认/验收规则，阶段操作使用明确动作。

选择工作项后在中央内容区域打开详情，保留列表筛选、滚动和选择以便返回。
详情包括概况、原始描述/附件、验收条件、设计、代码与验证、关联会话、历史；长正文使用现有 Markdown/FileViewer 能力。
原始导入或创建内容保留快照，后续修订有记录，不由同步脚本覆盖。

详情提供新建、标题/优先级/标签/仓库范围编辑、正文修订、附件、开始或继续会话、阻塞/解除、取消、归档/恢复及现有“移入回收站”。
归档和会话级联继续沿用当前“仅归档未被其他活动工作项引用的会话”规则。删除不能顺带丢失共享会话。
“移入回收站”需要确认，移动整个工作项目录到既有 `.pi/trash/work-items/`，不永久删除文件，也不删除关联会话。
管理页的归档/回收站筛选提供相应恢复：归档使用现有恢复语义，回收站项原 key 未被占用时原子移回，记录恢复事件；冲突返回 409。

移动端复用同一工作项业务与详情组件，保持全屏列表→详情导航；看板以阶段筛选列表替代横向拥挤的桌面列。
触摸、窄屏与工作区切换不丢失未保存草稿，保留明确返回入口。

### 6.3 数据与会话联动

从 WorkspaceManager 抽出工作项组件与数据层；WorkspaceManager 继续负责工作区设置，不同时重写其其他配置功能。
中央页和聊天快捷面板使用同一个按 workspaceId 索引的数据缓存与 mutation 服务，成功操作同时刷新双方。
页面可见时统一每 5 秒增量刷新或重取列表，窗口重新聚焦时校验；后台页面停止轮询，同一工作区不启动两个轮询器。
先复用现有 agent_end 刷新和变更回调，不新增独立工作项事件服务器。具体缓存库/组件拆分属于实施者选择。

## 7. 人工交付流程与历史兼容

### 7.1 两种兼容状态

当前已有工作项与自定义 loop 直接使用旧 phase/status，不能在版本升级时强制把这些项改造成新流程。
第一阶段所有工作项统一进入管理页，保留已有格式、阶段和历史。
**本设计的默认选择**：标准交付流程由人显式启用；未启用的项继续兼容旧 loop 与普通工作项操作。
新建表单可勾选启用标准流程，缺省不勾选；外部脚本不传新字段仍按原格式导入。这个默认值需要用户在审阅设计时检查。

启用后新增可选 delivery 元数据，内部 protocolVersion=1，首版 mode=manual；未启用项没有此块。
item.phase 仍是阶段唯一权威，不再另存一份 delivery.stage。delivery 保存需求/设计版本、确认与证据引用等流程元数据。
文件外层 schemaVersion 保持现有兼容格式，解析和序列化都透传该已知可选块；未知协议版本显示配置错误，不能静默按旧项执行。

### 7.2 标准流程

| 主阶段 | 进入/完成所需的人工作业 |
| --- | --- |
| 待梳理 intake | 明确原始需求与范围，开始设计 |
| 需求设计中 design | 填写可检查的验收条件和方案，人工确认当前版本 |
| 待开发 ready_for_implementation | 设计已确认；由人开始开发或打开执行会话 |
| 开发中 implementation | 记录各关联仓库的候选提交与自测说明，提交验证 |
| 测试中 verification | 按验收条件记录指定候选的检查结果，失败返回开发或设计 |
| 待发布 release_ready | 当前候选验证通过，填写发布/回滚说明，等待实际发布 |
| 已发布 released | 人登记版本/提交、环境、发布结果和必需检查，不能只把 status 改成 done |

需求/Bug 共用此基础流程；Bug 可采用简短的修复方案，但不能省略验收依据。首版不引入子任务执行模型。
等待确认和阻塞是阶段上的标记及总体 blocked 状态，不再增加对应的常驻 agent。
phase 增补 ready_for_implementation、release_ready、released；旧 analysis、requirement_approval、plan_approval 和 complete 继续可读。
旧分析/确认子阶段在看板投影到设计组并显示原始阶段标签；旧 complete 显示“历史已完成”，不推断已经部署发布。
看板提供折叠的历史完成分组，列表仍能检索；显式纳入标准流程时由人选择实际起点并补齐对应依据，不伪造历史确认。

标准项 generic PATCH 不能直接跳 phase/status 以绕过规则。流程命令统一由扩展检查后更新；旧项继续兼容原更新接口。
旧 loop 候选工具默认只返回未启用标准流程的项；显式查询可只读看到标准项并返回 managed 标记。
现有按合同执行、立即跑一轮对旧项保留；标准项第一阶段只提供普通会话/人工流程，不自动把旧一轮全流程合同强塞进新门禁。

### 7.3 确认、验证、返工与版本

设计确认绑定当前需求版本和设计内容摘要；需求内容变更使相关确认及下游证据失效。
候选以每仓库 `{repositoryId, commit}` 记录，验证结果绑定全部候选与验收版本；候选变化不能继续沿用旧通过结果。
标题、标签、优先级和会话链接变化不自动作废验收。
第一阶段验证可以是人工登记的结构化检查记录，明确标示记录来源；它不等于程序已执行测试。
无法执行的检查标为未验证/阻塞，不作为通过。首版不为“自动验收通过”增加新的命令执行器。

返工必须记录原因：实现问题回待开发；需求/方案问题回设计；环境问题保留当前阶段并阻塞。
首版不提供豁免或跳过门禁的“例外通过”。检查可以由人实际完成并记录，但未验证、失败或缺失依据都不能作为通过推进。
取消、归档或回退阶段保留已发生的产物、会话和事件；历史报告可查看但标明已失效。

输入变化的回退是确定性规则：设计确认前在设计阶段保留草稿；已确认后修改需求或方案，撤销该确认及下游有效证据，回设计阶段等待重新确认。
测试中或待发布时替换候选，保留历史报告但撤销其有效性，回开发中，重新提交验证。
已发布项的需求依据、确认方案、发布候选与发布登记作为已交付基线冻结；需要后续改动时创建关联后续项，不重写已发布事实或隐式开启同项新一轮流程。
已发布项仍可修改展示信息、添加追记、关联会话或归档，这些操作不得改写已发布基线。

## 8. 导入、文件与一致性

### 8.1 导入即转交权威

沿用外部脚本向工作项 POST API 提交 external 的方式，不要求重做 importer 配置面。
扩展服务在写入锁内按 source + sourceId 查找活动和归档项：新来源创建；重复来源返回现有项，不覆盖任何本地业务内容。
同一来源的并发请求也只能创建一项。归档、取消或本地删除墓碑仍参与去重，不因再次同步自动复活。
现有“删除”是移到 `.pi/trash/work-items/`，其中保留的 item.yaml 即来源去重的墓碑；首版不提供永久清空带来源项的能力，不另建一套来源数据库。
导入去重扫描包含该回收站；返回既有回收站项时标示 existing_trashed，不把它重新放回活动列表。用户手动从文件系统删除墓碑不在自动恢复承诺内。
导入响应继续包含现有 WorkItemDetail 字段；可附加 importOutcome=created/existing/existing_trashed，分别用 201/200，旧脚本的成功判断仍可用。
普通无来源的手动创建不采用内容去重。已导入项的来源、初始描述和附件快照保留；源端删除不删除本地项。
来源后续变化的差异提示、源状态回写、自动覆盖标题/正文/附件不在本阶段范围内。

### 8.2 持久化与操作事务

继续使用 `<workspace>/.pi/work-items/{requirements|bugs}/<KEY>-<slug>/`，item.yaml 为当前状态、README 为可读正文、events.jsonl 为追加历史。
新增流程材料放在工作项内的 delivery/artifacts，初始需求快照与附件不被覆盖；运行态与高频锁/心跳排除 Git。
一次修改使用 workspace 互斥与 expectedRevision，读取、前置检查和原子状态写入在同一事务中完成。
角色/HTTP/导入共用服务入口；单进程也不能用“只有一个进程”替代异步请求互斥和幂等。

文件系统没有跨文件事务。状态更新携带稳定 operationId 和待追加事件记录，原子写 item 后追加事件；恢复按 operationId/eventId 查重补齐。
产物先写独立目录，状态只引用已发布的产物；孤儿产物不代表阶段成功。
Git 提交失败不回滚已经提交的业务状态，不向调用方谎报“操作未发生”；记录可重试的版本提交失败，避免重试制造重复事件。
继续支持既有独立 `pi-loop` CLI 与 Web 对同一工作区的协作：轮执行继续共用 `packages/pi-loop` 的轮锁和到期协议，不能另写一份宿主协议。
工作项扩展服务无论从 Web 还是 CLI 加载，均遵守同一套跨进程短写锁；现有进程内队列不能独自承担这个承诺。
锁按规范化工作区路径确定身份，持有者释放前核对 owner token，不能仅凭时间窗删除仍活动的短事务写锁；具体原子文件锁实现由实施者选择。
任意外部脚本直接编辑文件仍属于绕过协议的受信任写入，不宣称这些写入受服务门禁保护；同步脚本按约定走 HTTP API。

## 9. 接口、工具与权限边界

保留工作项 list/get/create/update/content/attachments/events 路由，补流程动作接口；中央页、侧栏和 LLM 工具均调用同一扩展服务。
标准流程提供 start-design、confirm-design、start-development、submit-verification、record-verification、prepare-release、record-release、
rework、block、unblock、cancel 等领域动作，具体 URL 组织属于实施者选择，错误应能区分不存在、版本冲突、缺失依据与未启用。
动作需要 expectedRevision 与 requestId，重复请求返回相同结果，不重复改阶段/追加事件。

人工确认、人工验证登记与发布登记从用户 UI/API 发起，记录 actor=user、时间与所指版本。
现有 LLM 工具可以写普通工作项及提出材料，但不新增“批准自己方案”或“伪装人工发布”的 agent 工具。
这是受信任本地系统的协作约束，不声称拥有 bash 的 agent 被 OS 沙箱隔离；不引入多人身份认证产品。

新管理面受 work-items capability 控制，不要求为手工管理开启 workflows；workflows 的后续自动执行含义不在本阶段激活。
所有文件与产物引用继续执行工作区路径约束，禁止路径穿越或符号链接逃逸；不扩大通用文件写 API。

## 10. 交付边界与验证

里程碑一完成单宿主切换及既有能力回归；里程碑二完成中央工作项管理、来源权威和人工流程。
两个里程碑都需保持 SDK 依赖版本与源码无变更，并更新 AGENTS.md 的实际基线，不能把设计提前记为已实现。

必须覆盖的验证行为：

1. 无 daemon 监听和进程也能创建、发消息、停止、fork、打开历史与子会话，普通对话事件协议保持。
2. SSE 慢客户端受限、断线重连不停止任务；热重载/重复加载不出现两个 owner、两份消息或两个 loop 定时器。
3. loop 定时/手动轮、暂停/停止、锁与补跑、会话自链接、归档行为保持；单轮清理不误杀其他会话。
4. 首次停机迁移和宿主退出能够阻止新执行，恢复不会自动重复发送 prompt；旧进程未知时不盲目接手。
5. 中央页与侧栏在创建、编辑、归档、恢复和导入后显示一致，切工作区不串数据；回收站恢复保留原 key 和来源去重，key 冲突返回 409。
6. 列表/看板筛选、详情返回、移动端、未保存草稿、深链刷新与浏览器前进后退正常。
7. 两个进程通过扩展服务并发导入同一 source/sourceId 只有一项；重复同步不改本地内容，不复活归档/取消/回收站项。
8. 标准项的确认与验证绑定版本；缺依据不能推进；旧 complete 不显示为已发布。
9. 旧工作项、旧 loop 工具和已有附件/关联会话仍可使用；标准流程项不会被旧全流程 loop 自动拾取。
10. 产物/状态/事件/Git 提交各崩溃点可恢复，重复动作不制造重复阶段或事件。

验证按实际变更运行 Node 测试、tsc、lint 和必要的浏览器交互检查，不运行 next build。
本次交付仅为设计；没有执行宿主迁移、启动/停止真实 daemon、修改 SDK 或运行用户工作区流程。

## 11. 本设计的默认选择与实施者自由度

需要用户在审阅时重点检查的默认选择：默认列表、工作区作用域中央页、右侧只作快捷查看；标准流程显式启用以兼容旧 loop；
旧完成记录不推断已发布；第一阶段人工登记验收与发布，不提供门禁豁免；已发布基线冻结，后续改动建关联项。
未确认中断按执行/loop 处理，不全工作区停摆；后续才引入自动领取和验证执行。

实施者可决定具体模块文件名、缓存实现、内部 helper、事件补写的数据结构与 URL helper；不能改变六层、单宿主、SDK 不动、
Pi Web 导入后权威、方案 A 和分阶段交付这些已确认边界。
